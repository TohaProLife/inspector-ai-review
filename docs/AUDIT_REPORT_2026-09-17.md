## 2. Что именно требуется решить

Задание — автоматическая камеральная сверка ПД, РД и ИД с контролем комплектности, актуальности редакций и доказательств. Единица вывода — **доказательная группа**, привязанная к объекту, параметру или атомарному правилу и сопоставимым редакциям. Это существенно сложнее поиска похожего текста или визуального diff двух страниц.

Рабочий путь должен быть следующим:

1. Принять реальные документы, зарегистрировать происхождение и контрольные суммы.
2. Проверить качество и состав комплекта, определить стадию и метаданные.
3. Найти актуальные утверждённые редакции; неоднозначность отправить на уточнение.
4. Извлечь значения, таблицы и графические признаки с координатами.
5. Для каждого правила определить применимость и достаточность источников.
6. Сравнить значения по предметному правилу, включая единицы, допуски и согласованные изменения.
7. Показать предварительный результат с проверяемыми доказательствами.
8. Зафиксировать решение инспектора, код причины, автора и время.
9. При дозагрузке пересчитать затронутую часть, сохранив историю.
10. Финализировать неизменяемую версию протокола; внешнюю отправку вести отдельно.

У ТЗ два важных ограничения: недостаток информации не является нарушением; различие документов не обязательно означает нарушение. Например, уменьшение одного значения может быть триггером, увеличение — нет; согласованная новая редакция может отменить прежнее требование.

## 3. Что уже сделано хорошо

**1. Правильно выбрана ценность продукта.** Документ, источник и решение инспектора важнее свободного ответа модели. Такой подход согласуется с ТЗ и может стать убедительным отличием на защите, если карточка строится автоматически из новых файлов.

**2. Хорошо разделены основные смыслы статусов.** В документации явно отличены кандидат, подтверждённое нарушение, неполнота, неприменимость и подозрение. Worker не создаёт `CONFIRMED_VIOLATION`; обязательная текстовая причина решения проверяется на сервере.

**3. Есть реальная инженерная работа в ingest.** Потоковый SHA-256, временное хранение, проверка формата, ограничения размера, проверка XML, ограничение DOCX-контейнера, AV-адаптер, дедупликация внутри объекта, отдельная связь одинакового содержимого с разными стадиями и защита от перезаписи — полезная основа. Это не просто нарисованная кнопка загрузки.

**4. Технологическое разделение разумное.** React для UI, Node для приложения, Python для обработки, PostgreSQL для долговременных данных, object storage для файлов и очередь для тяжёлых работ соответствуют природе задачи. Переписывать весь проект на другой стек сейчас не требуется.

**5. Репозиторий собирается.** TypeScript-проверка, 23 JS/TS-теста и 4 Python-теста проходят; отдельный production build успешен. Тесты на ingest содержательнее простых snapshot-проверок: проверяют лимиты, форматы, дедупликацию, стадии и отказ антивируса.

**6. Пользовательский сценарий уже можно обсуждать с инспектором.** Есть очередь, сравнение источников, причина решения и протокол. В браузере рабочее место выглядит спокойно; панель действий остаётся доступной, документные источники видны одновременно. Это хорошая заготовка для предметного usability-теста.

**7. Документация прямо признаёт большую часть ограничений.** `IMPLEMENTATION_STATUS.md` перечисляет отсутствие OCR, linking, persistence и RBAC. Такое разграничение стоит сохранить, но сделать ещё точнее в README и интерфейсе.

**8. Верно замечена непригодность положительного seed для измерения FPR.** Это важнее красивой, но необоснованной цифры точности. Отказ от оценки качества по одним положительным примерам — правильное методологическое решение.

## 4. Критические проблемы реализации

Приоритеты: **P0** — блокирует достоверный основной сценарий или целостность результата; **P1** — существенно мешает приёмке и работе; **P2** — улучшение эксплуатации/удобства после основного контура. Это приоритеты аудита, а не официальные баллы организатора.

### A01 — P0. Новые документы не анализируются

**Подтверждено исходниками.** [app.ts](/C:/progs/HackatonAI/apps/api/src/app.ts:122) завершает проверку через таймер 1,8 секунды. [store.ts](/C:/progs/HackatonAI/apps/api/src/store.ts:279) копирует `findingTemplates` из публичных checks в каждый новый запуск. Содержимое загруженных файлов на результат не влияет. Python worker не вызывается.

Последствие: новый объект может получить расхождения и evidence-файлы учебного объекта Тюменская, 5. Даже загрузка только ПД не меняет эту логику. Это нарушает центральное обещание продукта и объектную принадлежность доказательств.

Исправление: отдельный явный режим seed; обычный check работает исключительно с manifest конкретного запуска. До подключения анализа возвращать честное состояние «анализ не реализован/не выполнен», а не завершённую проверку. Затем подключить очередь, worker и сохранение результатов.

**Готовность:** вывод для нового документа зависит от его содержания; каждый evidence относится к тому же объекту и входной версии; публичные labels недоступны обычному inference-процессу. Отдельный тест должен проверять изоляцию источников, а не лишь сброс решений seed.

### A02 — P0. Сводка и уверенность не являются результатами вычислений

**Подтверждено исходниками и UI.** [store.ts](/C:/progs/HackatonAI/apps/api/src/store.ts:50) задаёт `negativeVerified: 117`, `notComparable: 3`, `suspicion: 2`, `total: 132`. Уверенность вычисляется по порядковому номеру карточки: [стр. 94 кода](/C:/progs/HackatonAI/apps/api/src/store.ts:94). В интерфейсе это называется «Оценка модели», а проверка объявляется завершённой.

Для пустого нового объекта `total` обнуляется, но сохраняются константы неполноты и подозрений. Реальных записей, объясняющих 117 отрицательных результатов и два подозрения, нет. Сумма, сходящаяся к 132, не доказывает исполнение матрицы.

Отдельно смешаны разные единицы: количество параметров, количество findings по помещениям и подозрения вне матрицы. Один параметр может породить несколько доказательных групп, поэтому эти числа нельзя складывать в один итог «132».

Исправление: считать сводку только из сохранённых результатов; отдельно показывать покрытие параметров, число доказательных групп и workload инспектора. Ввести статус выполнения `NOT_RUN/UNSUPPORTED/FAILED`, не выдавая отсутствие реализации за отсутствие документов. Некалиброванную уверенность заменить на «не оценена» либо явно маркированную эвристику.

**Готовность:** у каждой цифры есть раскрываемый список записей и однозначный знаменатель. Ни одно `NEGATIVE_VERIFIED` не возникает из константы.

### A03 — P0. Worker — сравнение готовых строк, а не движок предметных правил

**Подтверждено исходниками.** [pipeline.py](/C:/progs/HackatonAI/services/worker/inspector_worker/pipeline.py:58) сравнивает заранее переданные `expected_value` и `actual_value` после пробелов и casefold. Извлечения из файла, числовой нормализации, допусков, направления изменения, определения применимости и утверждённой редакции нет. `process_job` проходит только по `job.rules`; наличие каталога из 132 строк не заставляет исполнить 132 правила.

Примеры предметных расхождений с таким подходом: 900 мм и 0,9 м могут означать одно значение; увеличение класса бетона и понижение класса не эквивалентны; изменение общей площади на 0,5% и 2% должно обрабатываться по установленному порогу. Это примеры программной семантики каталога, не правовое толкование норм.

Кроме того, worker без выполнения OCR и linking возвращает им `COMPLETED`: [pipeline.py](/C:/progs/HackatonAI/services/worker/inspector_worker/pipeline.py:88).

Исправление: типизированные стратегии правил, реальные этапы pipeline, обязательные prerequisites, единицы и нормализация по типу поля. Каталог преобразовать в исполняемые контракты; непокрытые правила честно учитывать отдельно.

### A04 — P0. Финализация не обеспечивает неизменяемость

**Подтверждено исходниками; отдельная динамическая проверка обходов не проводилась.** В [store.ts](/C:/progs/HackatonAI/apps/api/src/store.ts:354) финализация проверяет только наличие `CANDIDATE`, без полной проверки состояния обработки. Методы решений и reprocess не содержат запрета изменения финализированного check; загрузка проверяет наличие объекта, но не его финальный статус.

По ТЗ, стр. 22, после финализации запрещены дозагрузка и изменение статусов. Отмена разрешена только специальным ролям с причиной и аудитом. Простое выставление `FINALIZED` этого не обеспечивает.

Исправление: серверная таблица разрешённых переходов, транзакционная финализация, контроль версии записи, отдельная операция отмены и обработка повторного запроса. Условие готовности должно включать окончание всех jobs текущей входной версии, а не только отсутствие кандидатов.

### A05 — P0. Версии протокола не фиксируют содержание

**Подтверждено исходниками.** `ProtocolVersion` хранит метаданные и статистику. [Экспорт](/C:/progs/HackatonAI/apps/api/src/app.ts:182) берёт текущие findings проверки, а не снимок на момент создания версии. [recalculate](/C:/progs/HackatonAI/apps/api/src/store.ts:428) обновляет статистику последней версии. `completeCheck` заново записывает список протоколов с одним черновиком.

Следствие: у исторического протокола нет гарантии стабильного содержания; повторная обработка не сохраняет историю так, как обещано в документации. Экспорт черновика также исключает необработанные кандидаты, хотя предварительный протокол по ТЗ должен их содержать.

Исправление: immutable snapshot состава входа, результатов, решений и версий; hash снимка и отдельное хранение экспортного артефакта. Новые решения и дозагрузка формируют новую версию. Экспорт конкретной версии читает только её содержимое.

**Готовность:** повторное скачивание версии V1 после работы с V2 даёт тот же смысловой snapshot и проверяемый hash; все разделы предварительного/финального протокола согласованы с ТЗ.

### A06 — P0. Нет долговременного состояния и доставки результатов

**Подтверждено исходниками.** API использует `Map`, не PostgreSQL. Это справедливо и при запуске Compose: переменная `DATABASE_URL` сама по себе не меняет реализацию `InspectorStore`. RabbitMQ consumer печатает результат в stdout и подтверждает сообщение; обратного сохранения результата в API/БД нет. Надёжные retries и настроенная DLQ не обнаружены.

Рестарт теряет объекты, загрузочные записи, решения и протоколы, хотя бинарные оригиналы могут остаться в хранилище. Нельзя восстановить полную связь «файл→объект→проверка→решение».

Исправление: repository на PostgreSQL, persisted jobs, гарантированная публикация заданий и идемпотентная фиксация результата, подтверждение очереди после долговременного сохранения. На первом этапе достаточно модульного worker с несколькими этапами; восемь отдельных сервисов сейчас не обязательны.

### A07 — P1. Дозагрузка разрывает пользовательский сценарий

**Подтверждено в браузере и исходниками.** «Дозагрузить ИД» открывает «Новый объект проверки», с пустым адресом и действием «Создать и запустить анализ». Связь с существующим object_id в этот экран не передаётся: [App.tsx](/C:/progs/HackatonAI/apps/web/src/App.tsx:621).

Повторная обработка в store перезаписывает findings шаблонами, не вычисляет затронутые параметры и не сохраняет решения неизменившихся групп.

Исправление: режим добавления файлов к существующему объекту; новая версия manifest; dependency graph от файлов/редакций к результатам. Неизменившиеся доказательства сохраняют решение, изменившиеся отправляются на повторный review с объяснением.

### A08 — P1. Комплектность определена через наличие файлов

**Подтверждено исходниками.** Первый файл стадии выставляет `COMPLETE`: [store.ts](/C:/progs/HackatonAI/apps/api/src/store.ts:241). Worker делает то же и дополнительно считает каждый `RD_ID_MIXED` одновременно полноценной РД и ИД. Статуса PARTIAL в `StageSummary` нет.

Наличие файла не доказывает наличие требуемого акта, раздела, редакции или всех листов. Смешанный комплект требует классификации документов/страниц, а не автоматического закрытия двух стадий.

Исправление: отдельные уровни «файлы получены», «состав классифицирован», «достаточно для правила», «полный комплект по ведомости». Для неизвестного ожидаемого состава — UNKNOWN/PARTIAL. Каждое правило должно иметь собственные требования к источникам.

### A09 — P1. Evidence viewer пока не позволяет надёжно проверить вывод

**Подтверждено UI и кодом.** Отображаются два статичных PNG, `bbox` у всех seed-карточек null. Нет подсветки области, перехода к соседним страницам, реального открытия оригинала, выбора редакции, отображения статуса утверждения. Берутся только первые два evidence; полноценной ИД-панели нет. Общая ручка меняет CSS-ширину картинок в диапазоне 40–120%, но не реализует требуемый document zoom/pan.

На проверенном экране 1280×720 длинный лист ПД сжат до небольшого превью, подписи не читаются. Целевой фрагмент не выделен. Получается, что «источник рядом» выполнено, а «инспектор быстро проверяет конкретный вывод» — ещё нет.

Исправление: просмотр PDF/tiles в достаточном разрешении, fit-to-evidence, координатный overlay, независимый масштаб с опциональной синхронизацией, страницы и третий источник через tabs. Уверенность и риск не должны заслонять источник, редакцию и основание сравнения.

### A10 — P1. Submission не доказан как конкурсно совместимый

**Подтверждено:** официальный schema-файл отсутствует; тест проверяет выбранные поля, но не валидирует ответ по JSON Schema. `getSubmission` не имеет варианта `MISSING_DOCUMENT`; берёт только findings и требует предварительного решения человека. `location` уже изменён для UI: `012` превращается в `Помещение 012`, и эта строка уходит в экспорт.

**Риски, требующие методики:** неизвестно, допустим ли такой location, как матчить группы, какие поля/значения обязательны и разрешён ли ручной review перед конкурсной оценкой. Нельзя утверждать, что JSON точно отклонят, пока нет схемы и scorer. Нельзя и утверждать, что он им соответствует.

Исправление: вернуть официальный контракт; хранить машинный location отдельно от display label; сделать явный mapping всех статусов. Разделить автоматический конкурсный прогноз и юридически подтверждённый протокол. Не переносить запрет внешней передачи в ИАИС на автоматический scorer без прямого требования регламента.

### A11 — P1. Нет проверенной личности инспектора и достаточного аудита

**Подтверждено исходниками.** Входа и RBAC нет, автор решения приходит строкой из клиента, профиль и время последнего входа зашиты в UI. Audit table описана SQL, но действия туда не записываются. CORS допускает произвольный origin; инфраструктурные сервисы опубликованы через порты с демонстрационными настройками доступа.

Исправление: минимальная сессия пользователя, серверное определение автора, роли inspector/admin/ML engineer и отдельное право отмены финализации. Проверка принадлежности объекта, append-only история действий с request_id, actor_id, before/after, причиной и временем. Контур демонстрации и контур публикации должны иметь разные настройки сети и секретов.

Это статический вывод о защитных механизмах; эксплуатация уязвимостей и проверка обходов не выполнялись. `npm audit = 0` не подтверждает корректность прикладной авторизации.

### A12 — P1. Конфигурация Nginx не соответствует размерам загрузок

В [nginx.conf](/C:/progs/HackatonAI/apps/web/nginx.conf:1) не задан `client_max_body_size`. В официальной документации Nginx default — `1m`, при превышении возвращается 413. Следовательно, ожидаемый результат для поставляемого контейнерного web-прокси — отказ на обычных документах больше этого лимита, прежде чем сработают ограничения API. Вывод основан на конфигурации; контейнерный сценарий здесь не запускался.

Исправление: согласовать лимит HTTP-тела с пакетными 200 МиБ и multipart overhead; предел файлов проверять в API. Проверить timeout, buffering и временное дисковое пространство на реальной загрузке через web-порт. Источник: [Nginx — client_max_body_size](https://nginx.org/en/docs/http/ngx_http_core_module.html#client_max_body_size).

### A13 — P1. OpenAPI пока декларативный скелет

[openapi.ts](/C:/progs/HackatonAI/apps/api/src/openapi.ts:1) описывает только часть маршрутов, не содержит большинства request/response schemas, security scheme и определений path-параметров `{id}`. Получение JSON с `openapi: 3.0.3` ещё не означает валидный полный контракт или runtime-валидацию.

Исправление: единый источник схем, полное описание фактических endpoints и ответов, контрактная проверка. Отдельно описать адаптер к API `/api/v1/...` из ТЗ и mapping статусов, если внутренние имена сохраняются.

### A14 — P1/P2. Модель данных недостаточна для обещанной трассируемости

В SQL `UNIQUE(object_id, sha256)` вместе с одним полем stage не выражает уже поддержанную в памяти связь одинакового содержимого с несколькими стадиями. Нужны отдельные blob и logical document/stage associations.

Нет полноценной модели ревизий, утверждения, преобразований координат, evidence_group, нормативных версий, датасетов и моделей. `EvidenceRef` не несёт шифр, revision, approval_status и polygon. Для хранения оригинала upload record не фиксирует `object_key`, что затруднит последующее чтение, особенно при другом имени файла-дубликата.

Исправление: сначала согласовать минимальную доказательную модель, затем подключать persistence. Контрольные ограничения, индексы и внешние ключи должны отражать реальные связи. Для bbox определить формат `xyxy` или `xywh`, начало координат и transform; запись «числа от 0 до 1» недостаточна.

### A15 — P1. Проверка повреждённых PDF не реализована в полном смысле ТЗ

Определение PDF в ingest проверяет начало `%PDF-`, MIME и расширение. Это не доказывает целостность документа, наличие читаемых страниц и возможность рендера. Существующий upload-тест использует короткий искусственный буфер с PDF-заголовком, а не полноценный строительный PDF.

Исправление: после антивируса выполнять ограниченный по ресурсам разбор структуры и рендер контрольной страницы, фиксировать зашифрованные, повреждённые и нечитаемые документы отдельными состояниями. Требуются реальные корректные тестовые документы и репрезентативные случаи ошибок; нельзя считать успешное сохранение байтов успешным парсингом.

### A16 — P2. Сбои и длительная обработка слабо представлены в UI

Polling не обрабатывает ошибку запроса локально; переход по любому статусу, отличному от PROCESSING, ведёт в результаты, без полноценного FAILED-flow. Нет восстановления контекста проверки по URL. Дополнительные фильтры и меню документов — кнопки без обработчиков. «Запросить уточнение» меняет статус, но не создаёт адресуемый запрос с получателем и сроком; это нужно явно отразить в интерфейсе.

Исправление: route на object/check/finding, обработка ошибок и повтор, состояния jobs из API, видимый статус доступности анализа. Удалить или отключить незавершённые действия с объяснением. В поисковом диалоге проверить focus trap/возврат фокуса; наличие `aria-modal` и CSS focus само по себе не доказывает доступность.

### 6.1. Ошибки и пропуски документации, влияющие на решение команды

**Образец протокола нельзя целиком объявить необязательным.** `docs/README.md` и `MATERIALS_ANALYSIS.md` называют старые DOCX лишь визуальными/терминологическими примерами. Но ТЗ, стр. 18, прямо требует содержание и оформление из Приложения №2. Корректно: актуальное ТЗ переопределяет конфликтующую семантику статусов, а структуру и обязательные реквизиты приложения нужно сохранить. Сначала получить само приложение.

**Пропущен самостоятельный порог локализации.** Не только IoU ≥0,5: не менее 95% групп должны иметь полный комплект корректных доказательств. Локализация не сводится к красивому bbox в одном примере.

**High-модули исчезли из плана.** По таблице ТЗ управляемое дообучение и свободный поиск имеют High. Их можно ограничить для MVP по согласованному объёму, но нельзя считать необязательными просто потому, что основной экран уже готов. Минимум — полноценные данные/статусы, один содержательный сценарий и честная отметка остатка.

**Не отражены условия выпуска модели.** ТЗ требует object split, версионный GOLD после кураторской проверки, отсутствие падения recall по обязательной категории более чем на 2 п.п. и роста FPR более чем на 2 п.п., утверждение и rollback. Это не заменяется общим словом «дообучение».

**Не хватает usability acceptance.** Стр. 22: до 30 минут на 132 параметра/14 нарушений, не более трёх кликов на нарушение, тестирование на пяти инспекторах. Результат одного browser smoke-test этого не доказывает.

**Показатели производительности — цели, не результаты.** Нужны стенд, объём, hardware, cold/warm, число параллельных задач, median/p95, доля ошибок и стоимость. Таймер 1,8 секунды нельзя использовать в презентации как скорость анализа.

**SLA/RTO/RPO не обеспечиваются перечислением сервисов.** Ежедневный backup, указанный в ТЗ, сам по себе не даёт RPO 15 минут. Требуются более частое сохранение/журналирование и реально проверенное восстановление.

**Один и тот же scope называют разными статусами.** ТЗ разделяет процесс, верификацию, протокол и синхронизацию. Собственные статусы разрешимы как внутреннее решение, но нужен mapping; единое поле object.status не должно подменять все четыре измерения.

**Числа 60/15/15/10 и потолок 59 не подтверждены первичным источником в этом checkout.** Они повторены в двух Markdown-файлах, но это не два независимых доказательства. Пока методика не восстановлена, считать их условными данными прежнего анализа. В самом PDF установлено другое важное правило: непрохождение любого обязательного порога означает неприёмку даже при высокой общей F1.

**Требования и нормативные тексты нельзя смешивать.** В каталоге встречаются формулировки с правовыми последствиями и неоднозначными порогами. Они должны храниться как исходные данные, а их применимость и версии — проверяться отдельно. Этот аудит не подтверждает юридическую корректность каждого значения из каталога.

## 7. Каким должен быть минимальный реальный конвейер

Сохранять выбранный стек; уменьшить количество одновременно незавершённых подсистем. Один Python worker с явными этапами приемлем для начала. Отдельные процессы нужны по мере необходимости изоляции ресурсов, а не ради самой схемы из восьми сервисов.

### 7.1. Документ и provenance

Для каждого оригинала нужны стабильный внутренний ID, официальный file_id при импорте датасета, object_id, storage key, hash и происхождение. Физические байты, логические документы и назначения стадиям — разные сущности. Производные артефакты должны ссылаться на hash оригинала и версию преобразователя.

Вход каждого check — неизменяемый manifest с hash. Результат хранит dataset_version, matrix_version, model_version, rule_version, параметры запуска и input_manifest_hash. Для LLM-этапа также фиксируются версия промпта, конфигурация и использованные источники. Это позволит объяснить, почему две версии результата различаются.

### 7.2. Извлечение

Сначала определять, есть ли пригодный текстовый слой PDF; проверять его качество, затем использовать OCR там, где он нужен. Для крупных листов — ограниченный рендер и tiles с обратным преобразованием локальных координат. Таблицы, штампы и чертежи требуют разных обработчиков.

Полезный минимальный результат extraction: raw value, normalized value, type, unit, page, sheet, bbox/polygon, extractor version, confidence/quality, цитируемый фрагмент. Не терять исходное написание после нормализации.

DOCX/XML сейчас принимаются, но это не означает извлечение параметров из них. Для DOCX нужно согласовать стабильную локализацию: номер страницы возникает после контролируемого рендера; XML вообще не имеет естественной PDF-страницы. Конкурсная схема с `pdf_page_number` требует отдельного правила mapping для таких источников.

### 7.3. Связи и редакции

Порядок отбора: объект → стадия/дисциплина → шифр/марка → элемент/помещение/система → редакция/согласование → доказательство. Семантическая близость полезна для retrieval, но недостаточна, чтобы выбрать эталон.

Для пары сохранять причины связи, confidence, альтернативы и решение человека при неоднозначности. Нельзя сравнивать просто самые похожие страницы: одинаковые номера помещений возможны в разных секциях и на разных этажах.

Важный сценарий: более поздний файл без подтверждения утверждения не автоматически лучше раннего утверждённого. Если правило выбора не определено, результат — уточнение, а не кандидат на нарушение.

### 7.4. Исполняемый контракт правила

Минимальные поля сверх текущего каталога:

```text
rule_id, parameter_code, matrix_scope, version
applicability, required_sources, allowed_stage_pairs
entity_key, extraction_targets, data_type
normalization, unit_conversion, comparator, tolerance
revision_policy, approval_requirements
evidence_requirements, abstention_reason_codes
normative_reference_version, implementation_status
```

Сначала gate применимости, затем комплектность и актуальность, затем извлечение и сравнение. Разделить состояния выполнения программы и предметный статус: «правило не реализовано» не равно `NOT_APPLICABLE`; «OCR упал» не равно «документ отсутствует».

Для каждого числа явно определить направление нарушения, абсолютный/относительный допуск, обработку нулевого знаменателя, диапазонов и погрешности. Для классов — таблицу предметного порядка. Для отсутствия элемента — область и достаточность поиска, иначе возвращать недостаток доказательств.

### 7.5. Выбор первых правил

Не обещать сразу автоматизацию всей матрицы. Выбирать небольшой набор по доступности источников, ясности сравнения, повторному использованию extractor и важности для приёмки.

Предварительные кандидаты после восстановления TRAIN: PZ-002 (площадь и процент изменения), PZ-007 (этажность), KR-055 (класс бетона), PPM-103 (EI), ZU-125 (толщина теплоизоляции). Это предложение по инженерной декомпозиции; наличие пригодных значений и согласований в реальных файлах ещё нужно подтвердить. Для графического сценария выбрать один из публичных IOS4, предварительно разрешив конфликт mapping и обеспечив собственное извлечение, а не чтение gold values.

Один полностью проверенный контур должен включать также отрицательный результат, отсутствие доказательства и конфликт редакций. Три положительных красивых примера дадут меньше информации о качестве.

Не нужно вручную создавать 132 независимых pipeline: совместные extractors таблиц, ведомостей, чисел, марок и геометрии могут обслуживать несколько правил. При этом покрытие каждого parameter_code должно быть наблюдаемым отдельно.

### 7.6. LLM и свободный поиск

LLM целесообразно использовать для поиска релевантных фрагментов, структурированного извлечения, нормализации описаний и подготовки объяснения. Выход проверять по схеме, значения сверять с источниками, числа и пороги проверять детерминированно.

Документный текст — данные: он не должен управлять инструкциями модели, разрешениями инструментов или внешними действиями. Модель не назначает сама себе file_id, страницу и координаты, если они не подтверждены extraction layer. Для отсутствующего источника нужен явный отказ, а не восстановление «по смыслу».

Свободный поиск хранить отдельно от матрицы: `SUSPICION`, метод обнаружения, источники и следующий шаг. Перевод в `CANDIDATE` требует evidence; подтверждение — решения инспектора. Даже один реальный сценарий такого поиска полезнее фиктивного счётчика подозрений.

## 8. Оценивание качества: что измерять и как не обмануть себя

### 8.1. Полный набор требований ТЗ

| Контур | Что считать | Порог/условие |
|---|---|---|
| OCR | 1 − суммарный Levenshtein / число эталонных символов; CER, WER, coverage отдельно | Character Accuracy ≥0,95 |
| Ключевые поля | Exact Match после установленной нормализации | ≥0,90 |
| Linking | Верный объект, стадия, шифр и актуальная редакция evidence_group | ≥0,95 |
| Локализация | Верный file_id и страница; bbox/polygon IoU ≥0,50 | Полный комплект доказательств ≥0,95 групп |
| Detection | Precision, Recall, F1 по evidence_group с правильным типом и доказательством | ≥0,90 / ≥0,80 / ≥0,85 |
| False positives | FPR на проверенных отрицательных группах и устаревших редакциях | ≤0,10 |
| Отчётность | По объектам, разделам, типам; размер выборки, coverage/abstention, 95% CI | Обязательно |

Precision 0,90 и Recall 0,80 дают F1 примерно 0,847, поэтому выполнение двух минимальных порогов автоматически не гарантирует F1 ≥0,85. Проверять все ограничения отдельно, без округления до «почти выполнено».

### 8.2. Принцип независимой оценки

Сохранять **автоматические прогнозы до действий инспектора**. Результат после ручного подтверждения — отдельная метрика процесса review, он не измеряет качество модели. Текущий export, требующий обработки всех кандидатов, смешивает эти контуры.

Эталон на development/validation размечается отдельно; модель не получает ответы, значения и готовые доказательства из public checks как вход обычного inference. Public seed можно использовать для регрессии формата и known-example baseline, но его нельзя объявлять независимой тестовой выборкой.

По десяти положительным примерам нельзя оценить FPR и надёжность отрицательных выводов. Четыре группы одного объекта не поддерживают уверенные выводы о качестве на новых стройках. Присвоение отсутствующим labels значения «нарушения нет» недопустимо: это неизвестные данные.

### 8.3. Минимальный evaluation harness

1. Валидировать manifest, наличие разрешённых исходников, hash, split, уникальность ID и ссылки evidence.
2. Сформировать неизменяемый evaluation manifest; все страницы и редакции объекта держать в одном split.
3. Запустить inference по файлам без доступа к gold answers.
4. Сохранить raw predictions, нормализованный submission и технические ошибки раздельно.
5. Валидировать официальный schema; сверить коды, location, stage, page range и объектную принадлежность.
6. Сопоставить прогнозы и gold one-to-one по официальному правилу; повторные прогнозы не должны увеличивать число true positive.
7. Вычислить detection и evidence completeness, метрики извлечения и linking, confusion matrix статусов и причины abstention.
8. Выдать срезы по объектам/параметрам/типам документов и отдельную таблицу ошибок.
9. Зафиксировать версии, hardware, время, память, стоимость и hash результатов.

Правило matching для 10 checks и четырёх finding_groups необходимо получить из первичной методики. Нельзя самостоятельно выбрать удобную единицу зачёта и затем назвать метрику официальной.

### 8.4. Coverage и abstention

Нужно минимум три разных показателя: доля реализованных правил матрицы; доля применимых групп с достаточными входами; доля групп, где система выдала содержательный автоматический вывод. Высокая precision при отказе от большинства сложных случаев не означает хорошую систему.

Указывать число пропущенных обязательных групп и причины: неподдержанный формат, нет документа, плохое качество, конфликт редакций, не реализован extractor, техническая ошибка. Предписанный организатором учёт abstention в recall/scoring имеет приоритет; локально дополнительно показывать workload инспектора.

### 8.5. Разметка и доверительные интервалы

Нужны положительные, экспертно проверенные отрицательные, missing evidence, неприменимость, нечитаемые зоны, ошибки linking и устаревшие редакции. Добавленные синтетические документы полезны для регрессии, но должны учитываться отдельно от реального корпуса.

Доверительные интервалы рассчитывать с учётом зависимости страниц и findings внутри объекта. При двух доступных TRAIN-объектах объектная оценка обобщения будет очень нестабильной; это следует написать, а не скрывать за bootstrap большого числа страниц. Уточнить возможность дополнительного разрешённого development-корпуса и экспертной разметки.

Отчёт должен показывать числитель/знаменатель каждой метрики. Например, отсутствие ложных срабатываний на пяти отрицательных группах не доказывает FPR ≤10% в генеральной совокупности.

## 9. UX и презентационные материалы

Четыре Mobbin-референса разумно покрывают review, split view, очередь и статусы загрузки. Однако счёт и текстовый diff существенно проще крупноформатного инженерного листа. Из референса стоит брать организацию рабочего места, а читаемость, геометрическую привязку и сопоставление редакций проектировать по реальным документам.

**Для текущего UI в первую очередь нужны:**

- явная маркировка seed-режима и демонстрационных данных;
- подтверждённая источниками статистика вместо «132 проверены»;
- автоматическое приближение нужного фрагмента;
- редакция, согласование, ссылка на изменение рядом с выводом;
- отдельная загрузка к существующему объекту;
- фильтры уточнений, неприменимости и неполноты;
- код причины решения и разделение составного finding;
- просмотр истории конкретной версии;
- восстановление открытого объекта/check после обновления страницы;
- сообщения о техническом сбое, повторе и неисполненных правилах.

`NEGATIVE_VERIFIED` везде подписан «Отклонено». Для результата автоматической проверки без кандидата такая подпись неверна. Следует отображать «Расхождение не найдено» либо «Проверено: нет расхождения», а факт отклонения кандидата выводить как отдельное действие/происхождение результата.

В справочнике сейчас дословно отображается criticality, включая «приостановка работ» и «предписание». Сохранять исходную формулировку в provenance полезно; представлять её как готовое действие инспектору — неудачно. ТЗ прямо ограничивает риск очередностью review. В рабочем UI нужны нейтральные названия риска и ссылка на исходную классификацию.

**Концептуальные слайды нельзя использовать как подтверждение реализации или качества.** Они сгенерированы по промптам и содержат предметные ошибки:

- IOS4-079 превращён в насосы, хотя каталог описывает вентиляторы;
- AR-041 назван высотой помещения, а на другом слайде — запорной арматурой;
- номера источников в концепте отличаются от фактической public evidence;
- слайд протокола смешивает «подтверждено нарушение» и комментарий «соответствует ПД»;
- произвольные 94%, числа страниц, результатов и скорость не являются измерениями;
- на слайде карточки нет обязательного ввода причины;
- PDF-экспорт, подпись и версия 3 на картинке не подтверждают наличие этих функций.

Рекомендация: оставить слайды как архив концепта, явно подписанный в UX.md. Для защиты снять реальные экраны после исправления семантики, вставить настоящие source crops и реальные числа. Не тратить ближайший цикл на новую визуальную тему: текущая спокойная тема достаточна, основной дефицит — достоверность и удобство работы с доказательствами.

Существующий тест создания нового анализа проверяет наличие тех же десяти findings и отсутствие старых решений. Он защищает изоляцию решений seed, но одновременно закрепляет неправильную продуктовую логику переноса самих findings на новый объект. | Конфликт редакций | Уточнение, сохранённые альтернативы и причина выбора |
| Поворот/CropBox/tiles | Выделение попадает на исходный фрагмент |
| Дозагрузка | Тот же объект, новая входная версия, сохранены незатронутые решения |
| Финализация | Разрешена только в допустимом состоянии, финальный snapshot защищён |
| История | V1 воспроизводится после создания V2 |
| Рестарт | Объекты, решения, файлы, jobs и версии восстанавливаются |
| Повторная доставка job | Один результат для одной версии; старый job не заменяет новый |
| Два инспектора | Конфликт редактирования обнаруживается, история не теряется |
| Официальный submission | Полная валидация schema и references, правильный mapping labels |
| Web-прокси и загрузка | Реальный пакет допустимого размера проходит весь путь |
| Рабочий просмотр | Инспектор открывает нужную область и оригинал без ручного поиска по всему листу |

Тесты должны проверять эти гарантии, а не фиксировать наличие констант и CSS-слов. Расширять число тестов без закрытия предметных сценариев бессмысленно.

## 11. План доработки по зависимостям

Точного дедлайна и состава команды нет, поэтому сроки в часах были бы выдумкой. Ниже — порядок этапов и результаты, после которых можно переходить дальше. Роли — предложения для распределения работы, не утверждение о составе вашей команды.

| Этап | Работа | Ответственность | Gate завершения |
|---|---|---|---|
| 0. Достоверность | Изолировать seed; убрать фиктивные метрики/статусы; уточнить README | Backend + frontend | Новые файлы не получают seed findings; UI честно показывает границы |
| 1. Восстановить материалы | Официальные schema, split policy, scorer, приложения, разрешённые TRAIN-исходники | Ответственный за задачу/данные | Воспроизводимый источник, hash, лицензия/правила доступа, registry противоречий |
| 2. Сохранение и jobs | PostgreSQL, manifest versions, API→worker→результат, idempotency | Backend | Один настоящий job переживает рестарт и повторную доставку |
| 3. Извлечение и evidence | Реальный PDF, text/OCR, метаданные, координаты, просмотр | ML/document processing + frontend | Карточка построена из нового файла, фрагмент открывается точно |
| 4. Предметная сверка | Небольшой согласованный набор правил, актуальные редакции, положительные/отрицательные случаи | ML + предметный эксперт | Результаты воспроизводимы; есть содержательная локальная оценка |
| 5. Решения и версии | reason_code, роли, атомарность, immutable protocol, дозагрузка | Backend + frontend | Сквозной сценарий без потери решения и источника |
| 6. Оценка и экспорт | Frozen predictions, schema validation, matching, отчёт метрик | Data/ML + QA | Прогон одной командой; видны coverage и ошибки |
| 7. Закрыть остальные требования | Free search, GOLD draft/curation, дополнительные правила, администрирование | По владельцам модулей | Явная таблица выполненного/остатка, согласованный scope |
| 8. Репетиция сдачи | Чистый запуск, контейнерный upload, замеры, реальные скриншоты, demo fallback | Вся команда | Другой участник воспроизводит результат по инструкции |

Evaluation-каркас и разметку отрицательных случаев следует начинать уже на этапах 1–3. Ждать «готовой модели», чтобы впервые выяснить критерий matching, слишком поздно.

### 11.1. Что сделать раньше очередного улучшения дизайна

1. Перестать переносить seed findings в новые проверки.
2. Убрать ложные 117 отрицательных результатов и «оценку модели» из констант.
3. Восстановить официальный контракт сдачи и доступный корпус.
4. Подключить реальную обработку хотя бы одного документного сценария.
5. Защитить финализацию и сохранить snapshot протокола.
6. Реализовать дозагрузку к существующему объекту.
7. Исправить Windows check и лимит web-прокси.
8. Опубликовать внутри команды первый честный отчёт об ошибках и покрытии.

Первые два пункта не повышают ML-качество сами по себе, но убирают ложную картину готовности. Без них команда рискует оптимизировать интерфейс вокруг несуществующего результата.

### 11.2. Что пока не должно забирать основной ресурс

- Новая цветовая тема, дополнительные декоративные дашборды и шлифовка профиля.
- Разделение каждого Python-этапа в отдельный микросервис до появления сквозной обработки.
- Дообучение большой модели на десяти положительных примерах.
- Расплывчатый «универсальный агент», не имеющий проверяемого extraction/evidence-контракта.
- Реальная внешняя интеграция ИАИС раньше локальной целостности протокола, если организатор не установил иной приоритет: в таблице ТЗ у интеграции Low.
- Обещания 99,9% SLA и нормативной точности без стенда, измерений и процедуры эксплуатации.

## 13. Как защищать решение убедительно

Текущая формулировка, которую можно обосновать: «Мы реализовали рабочее место инспектора и контур загрузки; на публичных примерах показываем доказательную верификацию. Автоматическое извлечение и сверка новых документов ещё требуют подключения». Нельзя сейчас обосновать: «ИИ проверяет 132 параметра за две секунды».

Для следующей версии лучше подготовить короткий реальный сценарий:

1. Новый разрешённый комплект, которого нет в seed.
2. Реальная обработка с наблюдаемыми этапами и временем.
3. Найденный кандидат с точным фрагментом, выбранной редакцией и сравнением.
4. Проверенный отрицательный случай и один честный отказ от вывода.
5. Решение инспектора с кодом причины.
6. Дозагрузка в тот же объект, сохранение предыдущей версии.
7. Финальный протокол и отдельно валидный конкурсный прогноз.

Показать таблицу «реализовано / измерено / ограничение», размер validation-набора и реальные ошибки. Заранее подготовленные результаты допустимы как явно обозначенный кэш воспроизводимого прогона, но не как выдача label-файла за новый inference.

Главная продуктовая метрика помимо ML — время от открытия кандидата до обоснованного решения. Дополнительно: доля правильно отклонённых ложных кандидатов, число ручных переходов по документам и доля карточек с достаточной доказательной базой. Процент экономии времени можно заявить только после сравнения с ручной проверкой на сопоставимых задачах.

Преимущество для защиты может состоять в трассируемости и управляемости: каждый вывод связан с редакцией и источником, система объясняет отсутствие ответа, решения переживают дозагрузку, история воспроизводима. Сейчас это преимущество хорошо сформулировано в замысле, но ещё не закреплено центральной реализацией.

## 14. Решение для команды

**Сохранить:** продуктовый фокус на доказательствах, разделение кандидата и решения человека, выбранный стек, основу ingest, рабочую структуру UI и честное перечисление ограничений.

**Пересмотреть:** смысл «вертикального MVP», приоритеты ближайшей разработки, исполняемый контракт правил, единицы статистики, формат результатов и модель версий.

**Исправить до содержательной демонстрации:** seed на новых объектах, фиктивную сводку/уверенность, незащищённую финализацию, отсутствие snapshot, сломанную дозагрузку и неподтверждённый submission.

**Доказать измерениями:** извлечение из новых документов, linking, evidence localization, качество отрицательных результатов, coverage, время и воспроизводимость запуска.

Проект имеет пригодный фундамент; его не нужно начинать заново. Но готовность интерфейса сейчас значительно опережает готовность предметного движка. Самое ценное следующее достижение — небольшой, честный, воспроизводимый анализ новых документов с полными доказательствами и сохранными решениями. Он даст команде основание расширять покрытие и защищать результат фактами.
