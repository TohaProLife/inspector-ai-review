# Архитектурные решения и границы

Версия 1.3. Объяснение решений; справочные контракты находятся в 02–11. Хакатонные границы уточнены по [сессии Q&A](../HACKATHON_QA_SESSION.md).

## ADR-001. Модульное приложение и workers

Сохранить React, Node.js, Python 3.11+, RabbitMQ и Redis. Node-приложение разделить на модули identity, objects, intake, inspections, jobs, review, protocols, catalog, datasets, integration. Каждый модуль экспортирует команды/запросы; изменение чужого состояния выполняется через их контракт в общей транзакции.

Python-пакет содержит render, extract, metadata, link, evaluate и localize. Изначально один пакет и два пула: document и rules. Ресурсоёмкий OCR/CV при необходимости получает отдельный пул без изменения доменных контрактов. Outbox/scheduler и export/integration запускаются отдельными процессами.

Восемь отдельных микросервисов сейчас увеличат стоимость согласованности. Синхронный OCR внутри HTTP-запроса также отклонён: блокирует API и усложняет восстановление.

## ADR-002. PostgreSQL — доменная истина

Объекты, manifests, jobs, результаты, решения и ссылки на артефакты — в PostgreSQL. Redis содержит только восстанавливаемые данные; его потеря не отменяет решения и не разрешает повторный commit. RabbitMQ доставляет задания, а не хранит единственную копию их состояния.

Object storage хранит immutable bytes. Наличие S3-ключа не доказывает наличие валидного документа: нужна согласованная запись БД и принятый commit артефакта.

## ADR-003. Object, inspection и run различаются

Object — стройка. Inspection — цикл review и выпуска протокола. Analysis run — вычисление по одному frozen manifest. Дозагрузка в открытую inspection создаёт новый manifest/run, не изменяя прежние результаты. После финализации можно начать новую inspection того же объекта.

Таким образом, запрет дозагрузки после финализации относится к циклу проверки, а не навсегда закрывает объект.

## ADR-004. Раздельные статусы

Техническое выполнение, машинный вывод, review и протокол — разные измерения. CONFIRMED_VIOLATION является проекцией решения человека. Невыполненное правило не становится NOT_COMPARABLE ради заполнения матрицы. Legacy-статусы предоставляет адаптер.

## ADR-005. At-least-once и идемпотентные эффекты

Использовать transactional outbox, durable receipts, leases и fencing token. Повтор вычисления допустим; повтор применения результата исключается БД и проверкой текущей попытки. Exactly-once выполнение OCR не обещается.

## ADR-006. Снимки и журнал вместо изменения истории

Оригиналы, manifests, machine outputs, решения и snapshots append-only. Изменяемы активные указатели и техническое состояние jobs. Ошибка решения исправляется новым событием; отмена финализации не переписывает исходный артефакт.

Полный event sourcing не требуется: обычные таблицы плюс immutable версии и audit проще. Audit не заменяет данные, необходимые для открытия протокола.

## ADR-007. Гибридные правила

Модель находит/извлекает/объясняет; детерминированный исполнитель проверяет типы, единицы, пороги и prerequisites. LLM не придумывает нормативный порог, не исполняет инструкции документа и не утверждает нарушение.

Конкретные OCR/render/model providers выбираются через qualification gate: разрешённый dev-набор, качество, лицензия для коммерческого/государственного использования, offline-доступность и ресурсный бюджет. До реализации адаптера фиксируется один provider/version в release manifest; нельзя оставить выбор библиотек бесконечным. Передача документов или фрагментов внешнему AI/OCR/VLM API запрещена; базовый профиль полностью локальный.

## ADR-008. Три разных выхода

Inference export строится из frozen machine predictions. Human protocol отражает review. ИАИС требует дополнительно финализации и действительности версии. Официальный submission schema и scorer не выдумываются: до получения источника адаптер UNVERIFIED_CONTRACT, внутренние контракты реализуются независимо.

## ADR-009. Изолированный demo

Demo работает с отдельными БД/bucket/профилем, имеет постоянный баннер и не отправляет ИАИС-запросы. Обычный runtime не импортирует public checks даже при недоступности модели. Доступ к кэшу всегда проверяется в контексте организации/объекта.

## ADR-010. Границы пилота

Первая поставка — одна организация, но organization_id и policy checks обязательны. Локальный вход по логину/паролю соответствует ТЗ; SSO и УКЭП реализуются адаптерами после получения контрактов заказчика. Внешние зависимости перечислены в [реестре](13_OPEN_QUESTIONS.md), с временным поведением и блокируемым gate.

## ADR-011. Два локальных provider-профиля

Статус: принято как целевая конфигурация; не означает, что providers уже внедрены или прошли qualification gate.

Приняты два resource profile с одинаковыми provider slots и доменными контрактами:

- `laptop-rtx4060-8gb-v1` — текущий AMD Ryzen 9 7940H, 16 logical CPU, NVIDIA RTX 4060 Laptop 8 GiB, 14 GiB видимой ОС RAM. PDFium, PaddleOCR PP-StructureV3 с PP-OCRv5 East Slavic, Bonsai 2 27B PTQ1_0 + Q8 projector через закреплённый PrismML fork llama.cpp, Qwen3-Embedding-0.6B с размерностью 1024. GPU-этапы выполняются последовательно; context ограничен 8192 tokens; concurrency модели равен 1.
- `server-h100-80gb-v1` — на стенде два H100 80 ГБ, но для команды используется не более одного физического GPU; до 24 physical CPU cores, 640 ГБ RAM и минимум 300 ГБ рабочего диска. PDFium, GPU PaddleOCR PP-StructureV3 с PP-OCRv5 East Slavic, Qwen3-VL-8B-Instruct-FP8 через vLLM, CPU Qwen3-Embedding-0.6B без reranker. Context ограничен 8192 tokens, VLM concurrency — 2; GPU memory budgets стартовые и требуют H100 soak при совместном использовании GPU.

Собственные детерминированные providers едины для обоих профилей: `metadata-hybrid-v1`, `linking-policy-v1`, `typed-rules-v1` и `evidence-validator-v1`. Модель и embeddings помогают извлекать и ранжировать, но не обходят hard gates, типизированные правила и evidence validation. Полный выбор, альтернативы, лицензии, точные параметры и блокеры описаны в [provider selection](15_PROVIDER_SELECTION.md).

На текущем laptop 19 сентября 2026 года перед provisioning осталось около 2,2 GiB свободного места в корневом разделе и 2,5 GiB доступной RAM. Установка model artifacts запрещена до освобождения минимум 20 GiB диска; рекомендуется 40 GiB для image cache и обновлений. Также нужны минимум 6 GiB доступной RAM. Профиль не переходит в CONFIGURED до локального smoke, quality evaluation, resource benchmark и фиксации hashes/лицензий в новом immutable release.

## ADR-012. Маршрутизация доказательств по параметру

Статус: принято как целевая архитектура 26 сентября 2026 года; не означает готовность исполняемого pipeline.

Контекст: 132 параметра требуют разных источников и способов извлечения. Поиск похожих знаков решает только часть графических проверок; он не выбирает актуальную редакцию, не связывает помещение и не доказывает предметное расхождение. Полный прогон визуальной модели по каждому листу добавляет стоимость и ложные кандидаты без пользы для текстовых и табличных параметров.

Решение: atomic rule задаёт обязательные стадии ПД/РД/ИД, scope сущности, типы фактов и доказательств. Сначала применяются границы объекта, редакции и применимости, затем выбираются разделы, листы и помещения. Из доступных источников извлекаются текст, таблицы и векторная геометрия; OCR запускается для отсутствующего или непригодного текстового слоя. Графический поиск на плитках высокого разрешения включается только для предусмотренного правилом визуального факта, если векторного анализа и текста недостаточно. Геометрические правила, шаблоны и модель с визуальным примером могут предлагать кандидатов, но их тип, подпись, подключение и помещение проверяются отдельно. Только затем typed comparator и evidence validator формируют машинный вывод. [Контракт этапов](06_DOCUMENT_PIPELINE.md), [правила](07_RULES_AND_EVIDENCE.md), [оценка](09_EVALUATION_AND_MODELS.md).

Альтернативы: библиотека пиксельных шаблонов не гарантирует покрытие новых стилей, масштабов и контекста; безусловный поиск YOLOE по всем листам не решает привязку и сравнение; немедленное обучение отдельного детектора требует полной разметки и не заменяет документный контур. Ни одна из этих альтернатив не становится обязательным этапом для всех 132 параметров.

Следствия: одна схема маршрутизации и доказательств работает с локальным и стендовым resource profile. Визуальный провайдер выбирается по проверенному качеству, лицензии и ресурсному бюджету, а не закрепляется этой ADR. Отсутствие элемента подтверждается только при доказанном покрытии поиска; неопределённость сохраняется как abstention. Дообучение рассматривается после измерения устойчивых пропусков на разрешённой объектно изолированной выборке. Текущий release и покрытие правил не меняются от принятия этой ADR.
