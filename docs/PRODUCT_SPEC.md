# Продуктовая спецификация

Версия 1.1, 18 сентября 2026. **Целевые требования**, не перечень реализованных функций. Хакатонные границы уточнены по [сессии вопросов и ответов](HACKATHON_QA_SESSION.md). Текущее состояние — [IMPLEMENTATION_STATUS](IMPLEMENTATION_STATUS.md); конкретные контракты — [архитектура](ARCHITECTURE.md).

## Назначение и ответственность

«Инспектор ИИ» помогает сравнивать проектную, рабочую и исполнительную строительную документацию по матрице 132 параметров. Пользователь получает проверяемые расхождения с оригиналами, редакциями, значениями и локализацией. Машина создаёт кандидатов; подтверждённое нарушение возникает только после решения аутентифицированного инспектора.

В хакатонном scope ПД — базовый источник для сопоставления с РД и ИД. Сервис не выполняет самостоятельную экспертизу ПД на соответствие СанПиН, СП и прочим внешним нормам. Нормативные ссылки объясняют правило или источник порога, но не расширяют предмет проверки за пределы сравнения трёх массивов. Свободный поиск также ищет междокументные расхождения, а не заменяет государственную экспертизу проекта.

Объект содержит несколько циклов проверки. Внутри цикла каждый анализ имеет неизменяемый состав входов и версии обработки. Дозагрузка создаёт новый анализ; предыдущие результаты и протоколы остаются доступны. Комплектность, выполнение анализа, предметный вывод, решение человека, финализация и обмен ИАИС — разные состояния.

## Роли

Инспектор загружает, анализирует, проверяет evidence, принимает решения и выпускает протокол в пределах выданных прав. Supervisor дополнительно может отзывать финализацию с причиной. Администратор управляет доступом и эксплуатацией, но не получает автоматически право экспертного подтверждения. ML engineer готовит модели и evaluation; curator проверяет GOLD; нормативный эксперт утверждает версии правил/источников. Один участник пилота может совмещать роли явно. Полная [матрица полномочий](architecture/11_OPERATIONS_SECURITY.md) обязательна для backend.

## Основной сценарий

1. Выбрать/создать объект и цикл проверки, определить дату среза и сценарий сопоставления.
2. Загрузить документы; получить пофайловый статус проверки и отчёт о комплектности.
3. Запустить анализ: rendering/OCR, metadata, редакции, linking, извлечение и правила.
4. Увидеть реальное покрытие матрицы, технические ошибки и предметные исходы раздельно.
5. Открыть evidence, сверить актуальные согласованные источники, подтвердить/отклонить/уточнить с обязательной причиной.
6. При необходимости разделить составную находку, дозагрузить или разрешить metadata conflict, выполнить новый run.
7. Сформировать и проверить snapshot, финализировать; получить неизменяемый протокол.
8. При подключённой ИАИС передать только подтверждённые записи действующего FINAL. Статус передачи не меняет статус локальной финализации.

## Документы и комплектность

Обязательный целевой вход полного ТЗ — PDF, DOCX, XML; 50 МБ/файл и 200 МБ/пакет. Для хакатона подтверждён PDF-first путь, включая послойные PDF из САПР; отдельный DWG-обработчик не требуется. Обязательность DOCX/XML в hidden test и интерпретация единиц/крупных файлов корпуса остаются Q-03/Q-08. Дополнительные DWG/архивы/TXT требуют согласованного адаптера либо явного UNSUPPORTED, без обещания анализа на основании одного успешного upload.

Сценарии FULL, PD_RD_ONLY, PD_ID_ONLY, RD_ID_ONLY, SINGLE_ONLY и PARTIALLY_LOADED описывают состав доступных стадий. Полнота конкретного сравнения определяется обязательными документами, разделами, элементами, редакциями и качеством. Отсутствующий документ не считается нарушением. Стадия может различаться по страницам одного mixed-файла.

Происхождение включает исходные bytes/hash, документ/версию, стадию, шифр, дату, подтверждение согласования, страницу/лист, координаты и причины выбора редакции. Последняя по имени или файловой дате редакция не обязательно последняя применимая согласованная. UNKNOWN/CONFLICTING approval требует уточнения.

## Матрица, свободный поиск и evidence

Каждый параметр связан с исполняемыми typed rules: applicability, источники, извлечение, нормализация единиц, comparator, допуски, нормативная версия и evidence requirements. Число найденных элементов может превышать 132. Нереализованное правило обозначается UNSUPPORTED; его нельзя выдавать за отрицательный вывод или обычный abstention.

Система различает CANDIDATE, NEGATIVE_VERIFIED, MISSING_EVIDENCE, NOT_APPLICABLE, NOT_COMPARABLE, CLARIFICATION_REQUIRED и SUSPICION на машинном уровне. Человеческие решения и execution failures сохраняются отдельно. Свободный поиск выдаёт обоснованные подозрения вне матрицы; promotion требует полноценного evidence и сохраняет историю.

Карточка содержит expected/actual, единицы, применённое правило/порог, объектную сущность, все источники и согласования, file/hash/page/sheet/locator, выбранные и альтернативные редакции, rationale и human history. Confidence допускает null; неоценённая уверенность не заменяется декоративным процентом. [Геометрия](architecture/06_DOCUMENT_PIPELINE.md) едина для pipeline, viewer и evaluation.

## Решения и выходные документы

CONFIRM, REJECT, CLARIFY и VERIFY_NEGATIVE имеют обязательные основания. Автор и время назначаются сервером. Ошибка OCR/linking не автоматически превращается в качественный отрицательный обучающий пример. После решения создаётся кандидат на разметку; GOLD появляется только после curation.

Финализация требует закрытых кандидатов, пригодного sealed run и валидного evidence подтверждённых записей. Явно неполный протокол допускается только с зафиксированным перечнем ограничений; это не полное соответствие ТЗ. После финализации изменения запрещены; уполномоченный отзыв создаёт отдельное событие, старый snapshot не переписывается.

Есть три независимых выхода: frozen автоматические predictions для конкурса; человеческий протокол из immutable snapshot; адаптер ИАИС. Экспорт predictions не ждёт review. Форма протокола сверяется с обязательным приложением №2; JSON/PDF/DOCX/XML формируются из одного snapshot по согласованному профилю. Для хакатона достаточно facade/endpoint, из которого ИАИС сможет забрать результат; live sandbox, MQ и credentials не обещаны. Сертификаты/ключи УКЭП не предоставляются, поэтому mock connector допустим, а Finalized не означает подписано УКЭП.

## Качество и эксплуатация

Цели ТЗ: OCR Character Accuracy ≥0,95; key-field Exact Match ≥0,90; linking ≥0,95; полный комплект evidence с верными file/page и IoU ≥0,5 минимум в 95% групп; Precision ≥0,90, Recall ≥0,80, F1 ≥0,85, FPR ≤0,10. Обязательны coverage/abstention, denominators, 95% CI и срезы. Методика и model release gate — в [09](architecture/09_EVALUATION_AND_MODELS.md).

Устно подтверждённая структура оценки: 75% — техническая часть, 25% — pitch/demo. В технической части особенно важны функциональная полнота сквозного пути, OCR, F1, Precision и Recall; точная формула не раскрыта. Hidden test может покрывать не все 132 параметра, но неизвестный состав выборки не разрешает подгонять реализацию только под public examples.

Целевой стек: React, Node.js, Python ≥3.11, RabbitMQ, Redis, REST/HTTPS/OpenAPI 3.0; PostgreSQL и object storage — проектное решение. Защита, антивирус, identity/RBAC/audit, TLS, резервирование, RPO ≤15 минут/RTO ≤1 часа и performance thresholds определены в [11](architecture/11_OPERATIONS_SECURITY.md). Доступность 99,9% и скорость на 100 пользователях требуют испытаний.

Рабочее место должно позволять пяти инспекторам пройти согласованный сценарий 132 параметра/14 отклонений за ≤30 минут, типовое решение — ≤3 осознанных действий от карточки до сохранённого решения по заранее зафиксированной методике. Сценарий 100 одновременных пользователей не относится к первому этапу хакатона и проверяется позже. Сроки, фактическая coverage и ограничения публикуются по релизам; внешние вопросы — в [13](architecture/13_OPEN_QUESTIONS.md).
