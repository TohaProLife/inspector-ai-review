# Bounded OCR v3: выбор листов по контексту РД-ОВ

Профиль `local-bounded-ocr-layout-v3` — опциональный для **нового** запуска
`PILOT_PZ002_PZ017`. По умолчанию остаётся v1. Для нового запуска после
совместного обновления API и worker задайте
`INSPECTOR_OCR_LAYOUT_SELECTION_PROFILE=v3` в env-файле стека. Неверное
значение отклоняется до создания проверки. Release закрепляет профиль,
`adapterVersion=3` и SHA-256 его канонической конфигурации
`7713191d66895088f5c1d8264896e3e19e732276cb9d6cfb19244e835ae3f373`.
Старые v1/v2 запуски сохраняют свои immutable release и читаются прежним API.

## Правило выбора

API и worker независимо используют только сохранённый `document-text-v2`.
Внутри одного PDF сначала ищут страницу `TEXT_LAYER_CANDIDATE` с **тремя**
фразами `разрешение`, `обозначение`, `-рд-ов` после NFKC, нижнего регистра и
сжатия пробелов. Затем в пределах следующих восьми страниц ищут
`TEXT_LAYER_CANDIDATE` с **тремя** фразами `основные показатели по рабочим
чертежам марки ов`, `на отопление`, `тепловой поток`. Лишь страницы
`OCR_REQUIRED` строго между двумя якорями становятся кандидатами. При
отсутствии пары якорей источник получает `SKIPPED_NO_SUBJECT_CONTEXT` и
ноль выбранных листов. Идентификаторы исходников и OCR с пустых листов
в выбор не входят.

Кандидаты сортируются по номеру страницы и распределяются round-robin между
исходниками по `sourceFileId`; всего максимум две страницы на запуск.
Источник свыше 64 MiB не сканируется. Расчётный рендер ограничен 25 млн
пикселей и 20 000 пикселей на сторону при 120 dpi. API сверяет выбранные
страницы, счётчики, исходный SHA-256, страницу, геометрию рендера с допуском
2 px, SHA-256 страницы, допустимые ID PDFium/PaddleOCR и точное содержание
профиля до сохранения результата. При неполных/неверных данных результат
отклоняется. Никакие OCR-строки не превращаются в findings.

Повторные выбранные страницы теперь могут читаться из
[durable OCR-кеша](DURABLE_OCR_PAGE_CACHE.md) с ключом по SHA PDF, странице
и профилям. Это не меняет выбор листов и проверку результата API.

## Почему выбрано это окно

На публичном обучающем пакете `TRAIN_PUBLIC` проверены исходные PDF F0150
(`30c456b308c9f9e7e5c7fb009217777b8ce754490ccc39d662f21ac30eab031b`)
и F0201
(`0c398d7bca356455568413a6fc3b14044b7e538a902251b80e2a5574d80184fd`).
Сохранённые текстовые артефакты в `output/bounded-ocr-20260927/` дают
структурный выбор F0201 p.7 и p.8; p.9 также подходит контексту, но
откладывается лимитом двух листов. F0150 не даёт пары якорей и abstain.
Ранее v2 выбирал F0150 p.295 (геодезическая легенда) и F0201 p.30
(разрезы вентиляции). Визуальный просмотр исходника показал на F0201 p.7
анкету теплоснабжения с типом отопительных приборов, на p.8 продолжение
с нагрузками отопления/вентиляции. F0150 p.32 содержит неоднозначную
таблицу площади и намеренно не продвигается. Это проверка релевантности
выбора листов, **не** проверка правильности OCR и не подтверждение ПЗ-002
или ПЗ-017. В F0201 смешаны признаки РД/ИД; stage может остаться
`UNRESOLVED`, даже если OCR считал текст.

## Проверка

```bash
npm -w apps/api run typecheck
npm -w apps/api test -- test/ocr-layout.test.ts test/ocr-layout-read.test.ts
PYTHONPATH=services/worker python3 -m unittest services.worker.tests.test_durable_ocr_layout
INSPECTOR_POSTGRES_ADMIN_URL=postgresql://postgres:password@127.0.0.1:5432/postgres \
  npm -w apps/api run test:postgres -- -t 'persists only bounded OCR_REQUIRED|pins optional OCR v2|pins OCR v3'
```

Интеграционный тест создаёт и удаляет отдельную тестовую БД. Старый v1
включён явно: проверяет чтение и immutable сохранение. V3 тест проверяет
новый release, текстовые якоря, отказ при подмене порядка страниц и
сохранение двух листов. После реального запуска проверяйте строки и PDF
в UI как неподтверждённые. Офлайн-скрипт
`scripts/verify-bounded-ocr-stage.py` поддерживает v1/v2/v3 и независимо
повторяет выбор страниц и рендер. Команда приведена в
[инструкции проверки](BOUNDED_OCR_VERIFICATION.md#команда-для-сохранённого-v3-артефакта).
