# Кеш адресного OCR в durable стадии

`DOCUMENT_OCR_LAYOUT` профилей `local-bounded-ocr-layout-v2/v3` выбирает
страницы по сохранённому `document-text-v2`. После загрузки исходного PDF
worker сверяет его SHA-256. Для выбранной страницы сохраняет результат в
именованном Docker volume `ocr-page-cache`. Durable правило `PZ-002`
использует тот же volume для адресного OCR фактов и перепроверки таблиц.
Это повторное использование между immutable run на том же Compose-проекте;
лимит bounded стадии **две страницы на run** и правила выбора не меняются.

Ключ включает SHA-256 PDF, идентификатор загруженного источника,
физическую страницу, число страниц, DPI, script, точные профили PDFium и
OCR. Идентификатор нужен, потому что сохранённый OCR-артефакт связан с
`sourceFileId`; одинаковые байты, загруженные под другим ID, не разделяют
запись. Результат содержит исходный SHA, координаты строк и content hash.
На каждом HIT worker снова проверяет хеш исходного PDF, схему, хеш
записи, идентификаторы профилей, страницу и геометрию OCR. Повреждённая
запись останавливает job; она не заменяется молча новым распознаванием.
Запись делается через временный файл и атомарное переименование под lock.

Кеш включается, когда у `extract-worker` или `worker` заданы одновременно
`INSPECTOR_DURABLE_OCR_CACHE_ROOT` и `OCR_LAYOUT_PROFILE_ID`. Базовый
Compose монтирует `/ocr-page-cache`; профили laptop/server задают
ID локального OCR. В core smoke без локального OCR-провайдера кеш не
активируется. Архивное офлайн-сканирование `TRAIN_PUBLIC` использует
отдельный [публичный кеш](PUBLIC_FAMILY_OCR_QUEUE.md) с проверкой manifest;
рабочий кеш не читает этот архив и не использует его как источник факта.

Кеш не делает страницу `TEXT_LAYER_CANDIDATE`, не подтверждает правильность
распознанной строки и не меняет findings/coverage. Им нельзя закрыть
оставшиеся 1 410 невыбранных страниц открытого индекса. Для чтения на
ином узле нужна своя копия volume либо новый OCR.

Проверка: `services/worker/tests/test_durable_ocr_cache.py` проверяет
HIT/MISS при изменении страницы и профиля, отказ на повреждённой записи,
смене исходных байтов и неверной геометрии. Тест адаптера повторяет v3
run с одинаковым SHA PDF: OCR вызывается два раза при первом запуске и
ноль раз при втором, при этом источник заново скачивается и хешируется.
Тест PZ-002 проверяет повторное обращение к одной странице через общий
кеш без второго вызова провайдера.
На homeserver отдельный реальный [smoke кеша](../../output/durable-ocr-cache-20260927/smoke.json)
на разрешённом F0144 p.3 получил `MISS_WRITTEN`, затем `HIT` с одинаковым
SHA-256 OCR-артефакта `104626c6…` и 312 строками. SHA-256 receipt:
`fc2cee95a912222f34af156ab40ab6b743a51e2d90592cd81d4acb33a58863de`.
Он использовал локальный CPU PaddleOCR sidecar и новый кеш-модуль
непосредственно. Затем два **durable run через очередь и API** на публичных
F0150/F0201 (`CHK-C1397D15`, `CHK-7B2B3C0F`) завершили 10/10 jobs с
первой попытки. Оба обработали F0201 p.7/p.8 и записали одинаковый SHA
стадийного OCR-артефакта
`3b0865824b1f919eaa23a8d53d5232977989e70144f2b53b25357c16ed912e99`.
После второго run два файла кеша сохранили время записи первого run
(17:01:58 и 17:02:05 UTC). Это свидетельствует о повторном использовании;
сам статус HIT прямо проверен отдельным реальным smoke и тестом адаптера.
По `job_attempts` стадия `DOCUMENT_OCR_LAYOUT` заняла 17 с в первом run
и 2 с в повторном, обе попытки `SUCCEEDED`; это замер на homeserver с
локальным CPU OCR, а не прогноз для H100.
Итог обоих run: `PARTIAL`, 7/125, 0 findings; кеш не изменил выводы.
Дальнейший [четырёхкратный E2E замер](DURABLE_CACHE_E2E_20260927.md)
проверил и общий OCR volume правила PZ-002: всего пять адресных страниц,
те же хеши результата, у повторного run стадия правил 17 с вместо 41 с.

Текстовый слой той же очереди имеет отдельный
[кеш PDFMiner](DURABLE_TEXT_LAYER_CACHE.md); ключи, объемы и правила
валидации двух кешей независимы.
