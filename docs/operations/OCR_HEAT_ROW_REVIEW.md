# OCR-строки тепловых нагрузок: помощь эксперту

Профиль `INSPECTOR_OCR_HEAT_ROW_PROFILE=v1` включается только с
`INSPECTOR_ANALYSIS_PROFILE=PILOT_PZ002_PZ017` и
`INSPECTOR_OCR_LAYOUT_SELECTION_PROFILE=v3`. Новый immutable release
закрепляет `typed-pz002-pz017-ocr-heat-v1`, версию адаптера 2 и профиль
`conservative-ocr-heat-rows-v1`. Старые release остаются читаемыми.

При выполнении `RULE_EVALUATION` worker получает сохранённый OCR v3 artifact
через внутренний fenced API и сверяет его SHA-256, размер, manifest и профиль.
Из обработанных листов он предлагает только строки стадии РД. Для
одностадийного файла стадия берётся из закреплённого manifest; смешанный
комплект требует явной проверенной карты страниц в source review. Также нужны
опознаваемые раздел и строка, согласованные кВт/Гкал·ч, достаточная уверенность OCR и координаты исходного
растра. Максимум ГВС с циркуляцией и средний расход различаются. При
неразрешённой стадии, испорченной единице или противоречивом пересчёте он
воздерживается. API независимо повторяет вывод из сохранённых строк, проверяет
источник и координаты при приёме результата и при закрытии run.

Сквозной контракт исполняет настоящий Python-экстрактор и передаёт его вывод
настоящему TypeScript-валидатору: одностадийный РД даёт два предложения,
смешанный файл без карты страниц — два воздержания, а проверенная РД-страница
смешанного файла — два предложения. Четыре подмены результата, хеша и OCR stage
отклоняются. Контракт прошёл локально и в smoke checkout homeserver; это
проверка алгоритма на детерминированном OCR fixture, не подтверждение текста
реального листа.

Выход `ocrHeatRows` — **подсказка для просмотра**. Он не создаёт факты PZ-017,
сравнение ПД↔РД, finding или новое покрытие матрицы. Совпадение хешей и
координат также не доказывает, что OCR прочитал слово или число верно;
оригинальный лист и увеличенный фрагмент доступны на экране ручной сверки.

На сохранённом OCR v3 `TRAIN_PUBLIC` F0201 p.7–8 проверенная карта стадий
оставляет оба листа `UNRESOLVED`: результат извлекателя — 0 предложений,
4 воздержания `PAGE_STAGE_UNRESOLVED`.
[Диагностический отчёт](../../output/ocr-heat-rows-v1-20260927/report.json)
привязан к DB SHA OCR stage
`3b0865824b1f919eaa23a8d53d5232977989e70144f2b53b25357c16ed912e99`.
При подстановке `RD` только для проверки алгоритма получаются 2 предложения
по ГВС; единица отопления p.7 остаётся нечитаемой, а пара вентиляции p.8
противоречит пересчёту. Подстановка не является решением эксперта и не
записывается в source review. Отдельный реальный OCR v3 F0202 p.7–8 при
`UNRESOLVED` также даёт 0 предложений и 4 воздержания.

Два полных homeserver run с этим immutable release завершились:
`CHK-D905DD61` (F0171+F0202) и `CHK-9C474C9A` (F0150+F0201).
Оба сохранили 0 предложений, 4 воздержания и 0 findings. Защищённый
`GET /api/checks/:id/pilot-results` возвращает ограниченный список OCR-строк,
полные счётчики и признак усечения только для активного доступного run;
старые release получают `ocrHeatRows: null`. Экран покрытия показывает
исходную строку, координаты и переход к оригинальному листу.
[Браузерный smoke на F0202](../../output/ocr-heat-review-20260927/coverage-f0202-expanded.png)
подтвердил четыре воздержания и открытие оригинального листа. Данные run,
хеши стадий и проверки описаны в [журнале homeserver](HOMESERVER_SMOKE.md#ocr-heat-review-aid-первый-сквозной-run-27-сентября).

Для реального подтверждения числа нужны экспертная проверка оригинального
листа и его стадии, актуальности редакции, согласования, связи комплектов и
сопоставимости состава ПД и РД. Пока эти условия не выполнены, PZ-017
остаётся частичным и вывод о нарушении не формируется.
