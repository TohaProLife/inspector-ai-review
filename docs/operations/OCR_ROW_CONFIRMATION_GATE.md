# Граница ручного подтверждения OCR-строки

`ocrTableRows` в run `CHK-1BD8477F` — только перечень геометрических
предложений. Он не участвует в `factFamily.facts`: текущий контракт
типизированного факта разрешает локатор `TEXT_BLOCK` и независимо проверяет
точный текст/координаты текстового слоя. Подменять им OCR-строку нельзя.

## Ручная проверка транскрипции

Отдельный opt-in журнал `ocr-row-transcription-review-v1` принимает решение
рецензента по одной OCR-строке из неизменяемого run. Запрос содержит SHA OCR
стадии и отпечаток строки; API повторно выводит строку из сохранённых OCR и
rule-артефактов, сверяет SHA исходного файла, страницы и рендера, индексы и
геометрию строк, затем добавляет неизменяемую запись с автором и основанием.
`CONFIRMED_TRANSCRIPTION` означает только прочитанные человеком подпись,
значение и единицу; `REJECTED` отвергает OCR-строку. При новом решении старое
остаётся в истории. Без реального действия рецензента ни одна строка не
считается подтверждённой.

Миграция 021 переносит **последнее проверенное решение** в неизменяемый
снимок следующего run с исходным run/stage, PDF SHA и отпечатком строки.
При чтении снимка происхождение проверяется снова. `REJECTED` перекрывает
прежнее подтверждение. Снимок не является предметным фактом; на F0202
реальных решений и снимков пока 0.

## Отдельное решение о предметной применимости

Миграция 023 добавляет append-only `ocr_row_applicability_decisions`.
`GET/POST /api/checks/:id/ocr-row-applicability-reviews` показывает кандидатов
из двух неизменяемых снимков конкретного run: решения о транскрипции и решения
об источнике. При записи и чтении API повторно проверяет исходные OCR/rule
артефакты, SHA PDF, страницу и рендер, отпечаток строки, решения и их hash,
стадию страницы и разрешённый для кода раздел. `APPLICABLE` доступно только
для подтверждённой транскрипции и актуального утверждённого источника;
`NOT_APPLICABLE` и `UNSURE` остаются отрицательными для вывода факта.
Решение содержит код, атрибут, стадию, ключ объекта, контекст и обоснование.
Оно не создаёт факт, покрытие или замечание.

На реальном F0202 нет ни человеческих решений о транскрипции, ни решений
об источнике. Поэтому положительную применимость для его OCR-строк никто не
назначал. Положительный и отрицательный путь проверяются только на
синтетических данных PostgreSQL.

Миграция 024 сохраняет последнее полностью перепроверенное решение по
источнику, строке, коду, атрибуту, стадии и элементу в неизменяемый снимок
следующего run. Более поздние `NOT_APPLICABLE` и `UNSURE` перекрывают
прежнее `APPLICABLE`. Метод чтения repository повторно сверяет происхождение,
решение и оба исходных снимка; отдельного HTTP-маршрута для этих снимков
пока нет. Реальных положительных снимков нет.

## Следующий контракт типизированного OCR-факта

После журнала и снимка нужен отдельный opt-in контракт факта с
версионированным локатором `OCR_ROW` и независимым API-валидатором при
сохранении, sealing и чтении. `typed-fact-v2` валидатор и отдельный opt-in
read-only API выводят кандидата только из проверенных трёх решений и
OCR-артефакта. Этот просмотр пока не закреплён в release и не сохранён
как stage artifact результата. Связь
фактов ПД/РД использует существующий отдельный append-only workflow;
сравнение требует одинаковый код/атрибут/объект, проверенные стадии,
согласованные текущие источники, группу связи, предметный контекст и
утверждённое изменение. До выполнения всех условий остаётся `ABSTAIN`.
Даже подтверждённая OCR-строка не должна создавать finding автоматически:
пилотные семейства сохраняют `REVIEW_ONLY`.

F0202 p.7 содержит OCR-строку «Строительный объем здания: 60997,93», но
публичный манифест относит PDF с SHA
`632379a0e541f0c81e6b03e5528946730b4433939c796db4fdc1e5c3fc8b71ee`
к `RD_ID_MIXED/OV`; PZ-004 требует ПД/ПЗ и РД/АР или РД/КР. Строка
не даёт подтверждённого факта PZ-004. F0202 p.9 содержит объём **помещения
ИТП**, что также не равно строительному объёму здания. Ни для одного из
этих листов нет утверждённой пары ПД/РД.
