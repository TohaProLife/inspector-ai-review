Обещанные на сессии файлы не считаются полученными, пока их нет в текущем workspace и не проверены hash/version.

## Что проверено

- техническое задание на 32 страницах;
- эталонная методика и открытая разметка;
- каталог 132 параметров;
- манифест документов и схема конкурсной выдачи;

## Суть продукта

Нужен сервис, который принимает проектную (ПД), рабочую (РД) и исполнительную документацию (ИД), связывает версии документов, извлекает значения 132 контролируемых параметров и формирует доказуемые кандидаты на расхождения.

Ключевой принцип: модель не подтверждает юридическое нарушение. Она формирует кандидата с источниками. Только инспектор может присвоить статус `CONFIRMED_VIOLATION`.

Минимальный сквозной процесс:

1. Загрузка файлов и безопасная распаковка контейнеров.
2. SHA-256, дедупликация, антивирусная проверка.
3. Определение объекта, стадии, раздела, шифра, ревизии и статуса согласования.
4. Выбор последней применимой согласованной ревизии.
5. Рендер страниц и OCR, включая крупноформатные чертежи.
6. Индексация фрагментов с координатами доказательства.
7. Сопоставление ПД ↔ РД ↔ ИД по каждому применимому параметру.
8. Создание карточек кандидатов, неполноты и запросов уточнения.
9. Решение инспектора с обязательной причиной.
10. Версионируемый протокол. Выгрузка наружу только подтверждённых инспектором записей.

## Фактическая структура открытого набора

### Манифест документов

`document_manifest.jsonl`: 416 записей, по одной на файл.

Поля:

```text
schema_version
file_id
object_id
corpus
dataset_role
split
relative_path
extension
size_bytes
sha256
stage
section
pdf_pages
annotation_status
exclusion_reason
duplicate_group
distribution_status
label_visibility
```

Состав:

- 203 файла `TRAIN_PUBLIC`;
- 213 файлов `TEST_HIDDEN`;
- 3 объекта;
- стадии: 172 ПД, 103 РД, 130 ИД, 10 `RD_ID_MIXED`, 1 `UNKNOWN`;
- форматы: 366 PDF, 20 ZIP, 11 7z, 7 RAR, 6 DOCX, 5 DWG, 1 TXT;
- 58 файлов `GOLD_SEED`, 358 файлов без разметки.

Следствие: фактический ingest шире заявленных PDF/DOCX/XML. Нужны контролируемая распаковка архивов и явный статус для неподдерживаемых форматов.

### Каталог параметров

`parameter_catalog_132.jsonl`: 132 уникальных параметра.

Поля:

```text
parameter_id
parameter_code
pd_section
parameter_name
unit
source_pd
source_rd
source_id
trigger
criticality
matrix_row
mapping_status
```

Критичность: 106 критических и 26 существенных параметров. Код параметра из этого файла должен быть главным идентификатором правила и конкурсного ответа.

### Публичная разметка

- 10 записей `public_train_checks.jsonl`;
- 4 группы в `public_train_finding_groups.jsonl`;
- все 10 примеров положительные: `VIOLATION_PRESENT`;
- доказательства относятся к ПД/РД;
- локализация открытых примеров — точный файл и номер страницы, без bbox.

Этого недостаточно для обучения надёжного бинарного классификатора и оценки false-positive rate. Открытые примеры лучше использовать как проверку контракта, а не как полноценный обучающий корпус.

### Конкурсная схема ответа

Корень:

```json
{
  "object_id": "...",
  "checks": []
}
```

Обязательные поля проверки:

```text
parameter_code
location
violation_label
evidence
```

Допустимые `violation_label`:

```text
VIOLATION_PRESENT
NO_VIOLATION
MISSING_DOCUMENT
COMPARISON_IMPOSSIBLE
```

Каждое доказательство содержит:

```text
stage: PD | RD | ID
file_id
pdf_page_number
```

Внутренняя модель продукта должна быть богаче этой схемы. Конкурсный JSON — отдельный выходной адаптер.

### Метрики открытого скоринга

- F1 обнаружения — 60%;
- точный файл и страница — 15%;
- нормализованное значение и статус — 15%;
- целостность документов и корректность split — 10%;
- пропуск любого утверждённого критического контрольного пункта ограничивает итог 59 баллами из 100.

## Реальный объектный архив

`14_Алтуфьевское_79Б.zip`:

```text
Алтуфьевское, 79Б/
├── Исполнительная документация/  # пусто
├── Проектная документация/       # 68 PDF
└── Рабочая документация/         # 10 PDF
```

Большинство имён содержат шифры, годы, даты, `Изм. 1`, номера разделов и дублирующиеся редакции. Нельзя выбирать документ по имени или дате отдельно. Нужны нормализация шифра, извлечение ревизии и проверка статуса согласования из самого документа.

Пустая стадия ИД должна давать неполноту или `MISSING_DOCUMENT`, но не автоматическое нарушение.

## Статусы: не смешивать

Статусы проверки:

```text
CANDIDATE
NEGATIVE_VERIFIED
CONFIRMED_VIOLATION
MISSING_EVIDENCE
NOT_APPLICABLE
NOT_COMPARABLE
CLARIFICATION_REQUIRED
SUSPICION
```

Отдельно хранить полноту стадий и документов. `MISSING_EVIDENCE` и отсутствие ИД — не доказанное расхождение.

## Рекомендуемая архитектура

```text
React
  ↓ HTTPS / OpenAPI 3.0
Node.js API и оркестратор
  ├── PostgreSQL: метаданные, проверки, решения, версии протоколов
  ├── S3-совместимое хранилище: оригиналы, страницы, фрагменты
  ├── Redis: статусы и кэш
  └── RabbitMQ
       ├── Python worker: unpack/hash/dedup
       ├── Python worker: render/OCR/layout
       ├── Python worker: metadata/linking/revision
       ├── Python worker: 132 rule checks
       └── Python worker: evidence localization
```

LLM полезна для поиска кандидатов, нормализации формулировок и объяснения. Источник истины — документ, правило, координаты доказательства и решение инспектора.

## Порядок реализации

1. Контракты `manifest`, `parameter catalog`, `submission` и внутренняя state machine.
2. Ingest, хеши, дедупликация, статусы стадий.
3. Рендер страниц, tiled OCR и индекс доказательств.
4. Связывание документов и ревизий.
5. Универсальный исполнитель 132 параметров.
6. Карточка кандидата с синхронным просмотром источников.
7. Решения инспектора, аудит и версионирование протокола.
8. Инкрементальная дозагрузка до финализации.
9. Конкурсный экспорт и локальный evaluation harness.

Для хакатонного демо: один полностью рабочий сценарий ПД/РД/ИД, кандидат с доказательствами, подтверждение/отклонение инспектором, повторный прогон после дозагрузки и финальный протокол. Движок должен обходить все 132 правила, даже если часть правил сначала возвращает обоснованный `NOT_COMPARABLE` или `CLARIFICATION_REQUIRED`.

## Важные расхождения материалов

1. Текущее ТЗ требует богатую evidence card с bbox/polygon. Открытая схема submission требует только файл и страницу.
2. В примере протокола расхождения названы готовыми нарушениями. Текущее ТЗ разрешает подтверждать нарушение только инспектору.
3. В легенде критичность связана с жёсткими действиями. Текущее ТЗ отдельно запрещает трактовать риск как автоматическое юридическое решение.
4. Открытая обучающая выборка содержит только положительные проверки. По ней нельзя честно измерить FPR.
5. В данных встречаются `RD_ID_MIXED`, `UNKNOWN`, архивы и DWG. Система не должна насильно сводить их к чистым PDF ПД/РД/ИД.

При конфликте семантики использовать текущее 32-страничное ТЗ как главный источник, а старые DOCX — только как примеры формы и терминологии.

## Презентация

Шаблон содержит 37 слайдов, формат 16:9, стиль ЛЦТ 2026.

Обязательный смысловой блок начинается после инструкций:

1. суть и уникальность решения;
2. команда, роли и контакты;
3. история команды и преодолённые сложности;
4. техническая и маркетинговая суть, дальнейшее применение;
5. затем подробности решения, рынок, бизнес, технология, уникальность и план развития.

Лучшие доказательства для презентации: работающий сквозной сценарий, точная карточка evidence, метрики F1/Recall/FPR, скорость одного объекта и демонстрация безопасного `abstention`, когда документов недостаточно.
